Architecture case study

A distributed order system that survives payment failures, duplicate requests, and concurrent buyers.

Three independently deployable Spring Boot services — orders, inventory, and payment — coordinated by Kafka instead of a shared database, implementing the SAGA pattern for distributed transactions, with real concurrency-safety and idempotency guarantees verified under load, not just claimed.

Why this exists

A normal CRUD app reads and writes one database. This doesn't.

Inventory, payment, and order status are three separate services with three separate databases — true database-per-service. There is no single transaction that can atomically reserve stock, charge a customer, and mark an order complete, because in the real world those are often genuinely separate systems. That constraint is what makes this an interesting engineering problem instead of a routine REST API.

Payment fails after inventory is reserved

There's no shared transaction to roll back. The system has to explicitly compensate — tell inventory-service to release the stock it already committed to. That compensating action is the actual SAGA pattern.

See the compensation flow →

A client retries a timed-out request

Networks are unreliable — a client that never got a response might retry. Without idempotency, that turns into a duplicate order, or worse, a duplicate charge. This system enforces idempotency at three separate layers.

See the idempotency layers →

Two orders want the last unit at once

Two concurrent requests can both read "1 in stock" and both decide there's enough. Proven under real concurrent load — 50 threads competing for 10 units, exactly 10 win, every time.

See the concurrency test →
System design

Three services. No shared database. One event bus.

Each service owns its data exclusively — no other service is allowed to touch it directly, not even for a read. The only way services talk to each other is by publishing and consuming Kafka events. Hover a node for what it owns.

order-service

inventory-service

Owns stock levels. Guards every reservation with a Redis distributed lock scoped to the productId, so two concurrent orders for the same item can never both succeed past what's actually available.

  • Database inventorydb (Postgres)
  • Locking Redis SET NX PX + Lua compare-and-delete unlock, TTL watchdog renewal
  • Publishes inventory-reserved, inventory-rejected
  • Consumes order-created, order-rolled-back
:8083

payment-service

Owns customer balances. Debits independently the moment it sees inventory-reserved — it doesn't wait for order-service to tell it to. Uses JPA optimistic locking instead of a distributed lock, since conflicts per customer are rare.

  • Database paymentdb (Postgres)
  • Locking JPA @Version optimistic locking + retry loop
  • Publishes payment-confirmed, payment-rejected
  • Consumes inventory-reserved

Choreography, not orchestration. There's no central conductor calling each service in turn. Every service independently subscribes to the events it cares about and reacts — payment-service reads inventory-reserved straight off Kafka, it never gets called by order-service directly. order-service happens to also listen to the same events to keep the order's status up to date, but it isn't in the critical path. This is a deliberate tradeoff, discussed honestly in Roadmap.

The SAGA pattern

An order's status is a real, enforced state machine.

Every transition below is validated in code against this exact table — an illegal jump (say, COMPLETED → ROLLING_BACK) throws rather than silently corrupting state, and a repeated status is a safe no-op instead of an error. That matters because Kafka only guarantees at-least-once delivery: any of these events can legitimately arrive twice.

Order status state machine

PENDING → INVENTORY_RESERVED → COMPLETED. Inventory reserved, payment confirmed, order done.

order-service/model/Order.java the actual validation 
private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED_TRANSITIONS = Map.of(
    OrderStatus.PENDING,             Set.of(OrderStatus.INVENTORY_RESERVED, OrderStatus.INVENTORY_REJECTED),
    OrderStatus.INVENTORY_RESERVED,  Set.of(OrderStatus.COMPLETED, OrderStatus.ROLLING_BACK),
    OrderStatus.ROLLING_BACK,        Set.of(OrderStatus.ROLLED_BACK)
);

public void transitionTo(OrderStatus newStatus) {
    if (newStatus == this.status) return;               // redelivery of an already-applied event: no-op
    Set<OrderStatus> allowed = ALLOWED_TRANSITIONS.getOrDefault(this.status, Set.of());
    if (!allowed.contains(newStatus)) {
        throw new IllegalStateException("Illegal order transition for " + id + ": " + this.status + " -> " + newStatus);
    }
    this.status = newStatus;
    this.updatedAt = Instant.now();
}
Event-driven communication

Services talk through Kafka, not through each other.

One topic per event type — simpler to reason about than a shared topic carrying multiple event shapes. Each service owns its own copy of the event record classes rather than a shared library, keeping the services independently deployable at the cost of some duplication.

Fault tolerance: dead-letter topics

Every listener retries a failing message 3 times, 1 second apart, before giving up and publishing the raw record to a <topic>.DLT topic — instead of blocking the partition forever or silently dropping the message. An operator can inspect order-created.DLT, inventory-reserved.DLT, etc. and decide whether to replay or discard.

Show the config 
var recoverer = new DeadLetterPublishingRecoverer(kafkaOperations,
    (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));
var backOff = new FixedBackOff(1000L, 3L);
return new DefaultErrorHandler(recoverer, backOff);

At-least-once, not exactly-once

Spring Kafka's default delivery guarantee means any listener above can run more than once for the same event — a retry, a consumer-group rebalance, a redelivered message. That single fact is the reason the idempotency layer exists: every consumer that causes a side effect (debit an account, reserve stock, change order status) checks whether it has already handled this exact order before doing anything irreversible.

Data ownership

Database-per-service, enforced, not just diagrammed.

There is no schema that any two services both read from. Each Postgres database is provisioned separately by infra/init-multiple-dbs.sh when the stack starts, and each service's JPA config only ever points at its own.

inventorydb

The reservation ledger makes reservations idempotent per order — see Idempotency.

paymentdb

Owned by payment-service.

accounts.version backs the optimistic lock; the payment ledger makes charges idempotent per order.

Trade-off, on purpose: no shared library for the Kafka event classes means each service maintains its own copy of OrderCreatedEvent, InventoryReservedEvent, etc. That's duplication — and it's the standard price of keeping services independently deployable instead of coupled through a shared JAR.

Concurrency safety

Two different strategies, on purpose.

Both services face "two writers, one row" — but the conflict profile is different, so the right tool is different. That contrast is the actual point of building both into one project instead of picking one and using it everywhere.

Why a lock: conflicts here are common — many orders can compete for one popular product at the same instant, so blocking upfront and making everyone else wait their turn is worth the cost.

  • SET key value NX PX 5000 — atomic acquire, only succeeds if nobody else holds it, with a TTL so a crashed holder can't lock a product forever.
  • Unlock runs a Lua script that checks the lock's value before deleting — so service A can never release a lock that service B acquired after A's already expired (the classic "delete someone else's lock" bug).
  • TTL watchdog: a background renewal thread extends the TTL every 2s for as long as the lock is held, via the same ownership-checked Lua script. Without this, a reservation that stalled past 5s (GC pause, slow query) would silently lose the lock mid-operation.
  • Retries acquisition up to 30× with a 50ms pause instead of failing immediately on contention — proven necessary by the stress test (see Testing): without the retry, 50 concurrent requests for 10 units produced only 1 success, not 10, because everyone bailed on their first failed attempt.
Show RedisLockService.java (acquire + unlock) 
public String tryLock(String productId) {
    String token = UUID.randomUUID().toString();
    String key = LOCK_PREFIX + productId;
    Boolean acquired = redisTemplate.opsForValue().setIfAbsent(key, token, LOCK_TTL);
    if (!Boolean.TRUE.equals(acquired)) return null;
    startRenewal(key, token);   // watchdog: extends TTL every 2s while held
    return token;
}

private static final String UNLOCK_SCRIPT =
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "  return redis.call('del', KEYS[1]) " +
    "else return 0 end";

public void unlock(String productId, String token) {
    stopRenewal(LOCK_PREFIX + productId);
    redisTemplate.execute(new DefaultRedisScript<>(UNLOCK_SCRIPT, Long.class),
        Collections.singletonList(LOCK_PREFIX + productId), token);
}

Why not a lock: conflicts here are rare — one customer almost never has two payments in flight at once, so it's cheaper to let both proceed optimistically and make the rare loser retry than to pay the cost of blocking on every single charge.

  • @Version on Account — JPA increments it on every update and includes it in the WHERE clause; a concurrent write from a stale read throws OptimisticLockingFailureException instead of silently overwriting the other transaction's debit.
  • The consumer catches that exception and retries up to 3 times, re-reading the account fresh each attempt — never retrying with the stale entity.
  • Third failure publishes payment-rejected with "too many concurrent payment attempts" rather than retrying forever.

@Transactional
public PaymentRecord attemptCharge(UUID orderId, String customerId, BigDecimal amount) {
    Account account = accountRepository.findById(customerId).orElseThrow(...);
    if (!account.debit(amount)) return recordRejection(orderId, "Insufficient funds");
    accountRepository.save(account);   // throws OptimisticLockingFailureException on conflict
    return paymentRecordRepository.save(new PaymentRecord(orderId, CONFIRMED, "Charged " + amount));
}

// in the Kafka listener:
for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
    try {
        return publish(paymentProcessingService.attemptCharge(orderId, customerId, amount));
    } catch (OptimisticLockingFailureException e) {
        if (attempt == MAX_RETRIES) return publish(recordRejection(orderId, "Too many concurrent attempts"));
    }
}

Defense in depth

Idempotency enforced at three separate layers.

A duplicate request can arrive two different ways — a client retry over HTTP, or a Kafka redelivery internally — so idempotency has to be enforced at both boundaries, not just the one that's easy to demo.

1

HTTP boundary — client idempotency key

POST /orders takes a client-supplied idempotencyKey. order-service checks for an existing order with that key first; if two requests race past that check simultaneously, a unique constraint on the column is the real source of truth — the in-memory check is just an optimization to avoid hitting it in the common case.

Show OrderController.java 
var existing = orderRepository.findByIdempotencyKey(request.idempotencyKey());
if (existing.isPresent()) return ResponseEntity.ok(OrderResponse.from(existing.get()));

try {
    order = orderRepository.save(order);
} catch (DataIntegrityViolationException e) {
    // Race: both requests passed the check above before either committed.
    Order winner = orderRepository.findByIdempotencyKey(request.idempotencyKey()).orElseThrow(() -> e);
    return ResponseEntity.ok(OrderResponse.from(winner));
}
2

Kafka consumer boundary — per-order outcome ledgers

Kafka's at-least-once delivery means onInventoryReserved or onOrderCreated can fire twice for the same order. PaymentRecord and ReservationRecord are written in the same transaction as the debit / stock update, keyed by orderId. Before doing anything, each consumer checks for an existing record and replays the recorded outcome instead of re-running the side effect.

This is what closes the double-charge / double-reservation bug: without it, a transient failure between "debit committed" and "confirmation published" would cause a redelivery to charge the customer twice.

3

Domain boundary — the state machine itself

Even if a redelivered event somehow reached the consumer after the order already finished, Order.transitionTo() refuses an illegal transition and no-ops on a repeated one (see SAGA Flow). Concretely: a redelivered PaymentRejectedEvent after an order already rolled back can no longer re-publish the compensating order-rolled-back event and cause inventory-service to release the same stock twice.

Failure handling

What actually happens when payment fails.

Walk through the exact sequence order-service runs when inventory was already reserved but the charge is declined — the compensating transaction that makes this a real SAGA implementation, not just a happy-path demo.

  1. 1

    Order reaches INVENTORY_RESERVED

    inventory-service reserved the stock and published inventory-reserved. payment-service picked it up independently and attempted to charge the customer — and the charge was declined (insufficient funds, or too many concurrent attempts on that account).

  2. 2

    payment-service publishes payment-rejected

    With a reason string attached ("Insufficient funds", etc). No money moved — the failed debit() call never persisted.

  3. 3

    order-service transitions the order to ROLLING_BACK

    This transition is only legal from INVENTORY_RESERVED — enforced by the state machine. A redelivery of this same event after the order already finished rolling back is rejected here and skipped, not re-processed.

  4. 4

    order-service publishes order-rolled-back — the compensating transaction

    This is the actual SAGA compensation step: since there's no shared transaction to roll back, order-service explicitly tells inventory-service to undo what it already committed.

  5. 5

    inventory-service releases the reserved stock

    The units go back into available(), under the same Redis lock used to reserve them.

  6. 6

    Order reaches ROLLED_BACK — terminal state

    The saga is done. The customer was never charged, and the stock is available again for the next order.

What isn't handled yet: the transition to ROLLING_BACK and the publish of order-rolled-back are two separate steps, not one atomic unit — a crash in between them would leave an order stuck in ROLLING_BACK with the compensating event never sent. A full outbox pattern would close this; it isn't implemented here. See Roadmap.

Honest status

What's real, and what's still a known gap.

Every claim on this page is checked against the current codebase, not the project's marketing copy. This section exists so nothing above has to be taken on faith.

Implemented & verified

  • Choreography-based SAGA with a validated, enforced order state machine
  • Redis distributed lock with TTL watchdog renewal for inventory reservation
  • JPA optimistic locking + bounded retry for payment
  • Three-layer idempotency: HTTP key, Kafka consumer ledgers, state-machine guard
  • Dead-letter topics with bounded retry on every Kafka listener
  • Redis cache-aside with eviction-on-write for order status reads
  • Concurrency stress test with a real, published result (50 threads / 10 stock)
  • k6 load test with a real, published result (8487 requests, 0 failed, all thresholds passed)
  • Single-instance AWS EC2 deployment, exercised end-to-end

Known limitations / roadmap

  • Choreography, not orchestration — failure-path logic is distributed across each service's consumers rather than driven by a central saga coordinator. Both are valid patterns; this project deliberately demonstrates the choreography approach.
  • No outbox pattern — the status-transition-then-publish sequence in the rollback path isn't atomic; a crash between the two can strand an order mid-rollback (see Failures).
  • Single-node Redis lock — not Redlock across multiple nodes; acceptable for this project's scope, not for a system handling real money at scale.
  • No distributed tracing — no correlation IDs propagated across services; logs live independently per service, making a full saga hard to trace by hand across three log files.
  • Terraform IaC removed — a managed-services AWS deployment path existed earlier but isn't part of the current repository.
